### わかったこと

- **メガシンカは `Gengar-Mega` のような種名指定だけで種族値・タイプ・特性が切り替わる**。チャンピオンズの中核要素がそのまま扱える。
- ダメージレンジ、確定数テキスト（`guaranteed OHKO` / `0.4% chance to 2HKO` 等）、Smogon形式の説明文がAPIから直接取得でき、UI表示に必要な出力は揃っている。
- テラスタルも `teraType` 指定で計算に反映される。将来のチャンピオンズへの導入時に追従可能。
- **注意点1**: タイプ無効（ダメージ0）のとき、`result.damage` は乱数16通りの配列ではなく単一の `0` を返す。BattleState側のハンドリングで考慮が必要。
- **注意点2**: ライブラリの種名・技名は英語入力。日本語UI→英語IDのマッピングテーブルが必要（`@pkmn/data` の翻訳データで対応予定）。

### 残タスク（ゲーム内実測との照合）

式レベルの検証は完了したが、**チャンピオンズ実機のダメージ実測値との照合は未実施**（実対戦のスクリーンショット/実測データが必要）。Phase 1で手動入力UIができた段階で、実対戦10ケース以上と照合する。特にZA新規メガシンカの種族値はShowdownデータに未反映の可能性があり、差分パッチの必要性をここで判断する。

## PoC 0-1: USBデバイスキャプチャ ✅

- 場所: `poc/capture/`（SwiftPM実行ファイル）
- ビルド: `cd poc/capture && swift build`（Swift 6.1.2 / macOS 15で確認済み）
- 実行方法:
  - `./.build/debug/poke-capture-poc list` — デバイス列挙（最大30秒待機）
  - `./.build/debug/poke-capture-poc capture 600` — 600秒間フレーム取得して統計表示

### 実装済みの内容

- カメラ権限（TCC）の確認と要求（未許可だとエラーなしで空リストになるため必須）
- `kCMIOHardwarePropertyAllowScreenCaptureDevices` の有効化（OSStatus確認込み）
- `DiscoverySession`（`mediaType: nil` で全列挙）ウォームアップ + RunLoopを回しながらの出現待ち + `AVCaptureDeviceWasConnected` 通知の併用
- `.muxed` メディアタイプによるスクリーンキャプチャデバイスの判別
- `AVCaptureVideoDataOutput`（BGRA指定）でのフレーム受信
- フレーム統計: 解像度、ピクセルフォーマット、5秒ごとのfps、ドロップ数、平均フレームレート

### 実機テスト結果（2026-07-12、iPad USB接続）

30秒テスト:

| 項目 | 結果 |
| --- | --- |
| デバイス検出 | 成功（`iOS Device` / muxed=true として出現） |
| 解像度 / フォーマット | **2360x1640 / BGRA**（iPad Air想定の画面解像度そのまま） |
| 初回フレームまで | セッション開始から約4秒 |
| 平均フレームレート | **59.0 fps**（立ち上がり後は57.5〜60.0で安定） |
| フレームドロップ | **0** |

10分（600秒）安定性テスト:

| 項目 | 結果 |
| --- | --- |
| 総フレーム数 | 25,138 |
| フレームドロップ | **0** |
| 平均フレームレート | **58.1 fps**（受信中は57.5〜60.0で終始安定） |
| 受信継続時間 | 約432秒（7.2分） |
| ⚠ 発見事象 | **テスト残り約2.8分でフレーム受信が停止**（エラー・切断通知なし、セッションは動作継続） |

フレーム停止の原因は**iPad側の自動ロック（スリープ）**の可能性が高い（受信中の品質に劣化はなく、ある時点から完全に止まる挙動）。次回、画面を操作し続けた状態 or 自動ロックをオフにして再確認する。

**本番設計への反映（重要）:** デバイスのロック・スリープでフレームは静かに止まる（エラーイベントが来ない）。本番サイドカーには「最終フレームからのタイムアウト監視（ウォッチドッグ）→ UIに『デバイスがスリープした可能性』を表示」を必ず入れる。ゲームプレイ中は画面操作が続くため実運用では問題になりにくいが、休憩・中断時の復帰処理が必要。

### デバッグで判明した重要な知見（本番サイドカー設計に反映すること）

初回実装ではデバイスが検出できず、以下3点の修正で解決した。

1. **カメラ権限（TCC）が必須**: 未許可だと`DiscoverySession`はエラーなしで空を返す。本番アプリでも起動時に`AVCaptureDevice.requestAccess(for: .video)`を呼び、拒否時の案内UIを用意する。
2. **待機中はRunLoopを回す**: デバイス出現イベントはRunLoop経由で配送される。`Thread.sleep`でポーリングすると受け取れない。
3. **DiscoverySessionは`mediaType: nil`で全列挙してから絞る**: `.muxed`を探索条件に指定すると出現前のデバイスが弾かれるケースがある。列挙後に`hasMediaType(.muxed)`で判別するのが確実。

その他:

- iPhoneのContinuity Camera（`muxed=false, video=true`）と画面キャプチャデバイス（`muxed=true`）が同時に列挙されるため、**muxed判定での区別が実際に必要**だと確認できた。
- OS警告: macOS 14+では `.external` にdeprecation警告が出るが、USBスクリーンキャプチャデバイスの列挙は `.external` が現行の正解。将来のmacOSでの挙動変化は監視。
- プロパティ設定→反映まで数秒のラグ。本番サイドカーは「起動時に有効化して常駐」の設計（プラン通り）が正しい。
- 生データレートは 2360×1640×4byte×60fps ≒ **890MB/s**。PoC 0-2の転送方式は「毎フレーム全画素をWebViewへ送る」案が非現実的なことがこの時点で確定。表示用はダウンサンプル/エンコード、認識用はサイドカー内で完結させる方針が妥当。

## PoC 0-2: フレーム→Tauri転送 ✅

実施日: 2026-07-12（iPad実機 + ポケモンチャンピオンズ起動状態）

### 採用方式: 候補C（サイドカーからのMJPEG配信）

候補Cを最初に実装・計測したところ、目標を大きく上回る結果が出たため**この方式で決定**。候補A（WebSocket + canvas描画）・候補B（共有メモリ）の実装比較は不要と判断した。

構成:

```
Swiftサイドカー (poke-capture-poc stream)
  キャプチャ(2360x1640 BGRA)
  → CIContextで0.5倍縮小(1180x820) + JPEG(quality 0.6)
  → 127.0.0.1限定の自前HTTPサーバー(Network.framework)からMJPEG配信
Tauriアプリ (poc/viewer)
  <img src="http://127.0.0.1:8787/stream"> で表示（自動再接続つき）
```

### 計測結果

| 項目 | 結果 | 判定 |
| --- | --- | --- |
| 体感エンドツーエンド遅延 | **ほぼ同時（0.1秒以下）**（ユーザー実機確認） | ◎ 目標200ms以下を余裕でクリア |
| サイドカーCPU使用率 | **約10%**（キャプチャ+縮小+JPEG+配信込み） | ◎ LLM・認識と同居可能な水準 |
| 実効フレームレート | 約19fps（設定上限30fps） | ○ 表示用途には十分。改善余地あり(下記) |
| 平均フレームサイズ | 75KB（≒1.5MB/s） | ◎ ローカル転送として余裕 |
| Tauriアプリ | 雛形作成→Rustビルド30秒→表示まで問題なし | ◎ |

### 実装上の知見・残改善点

- **fps間引きのジッター**: `minFrameInterval` 経過判定のみの単純スロットリングだと、入力フレームの到着タイミングとの位相ずれで実効fpsが上限の6割程度になる。Phase 1では「次フレーム送信予定時刻」ベースのスケジューリングに直す。
- **stdoutバッファリング**: パイプ経由で実行するとログがブロックバッファリングされ観測しづらい。`setbuf(stdout, nil)` を追加済み（次回ビルドから有効）。
- MJPEGは1クライアント≒1.5MB/sなので、将来「ゲーム画面+認識デバッグ画面」など複数ストリームにも耐えられる。
- 高圧縮・低遅延をさらに追うならH.264(VideoToolbox)+WebRTC/HLSがあるが、現状の数値では**不要な複雑化**。MJPEGで確定してPhase 1に進む。

### PoC 0-1の追加知見（デバイス再接続）

- ケーブル抜き差し後は数秒で再列挙される（22:58の再接続確認で即検出）。一方、**接続が切れた状態ではiPhoneのContinuity Cameraのみが列挙され続ける**ため、「外部デバイスあり≠キャプチャ可能」の区別（muxed判定）が実運用でも必須。
- 本番サイドカーには「デバイス喪失→再探索ループ」の実装が必要（PoCではプロセス再起動で代替）。

## 名前OCR PoC（2026-07-17）

実対戦のiPadキャプチャから通常対戦HUDの名前領域を切り出し、Apple Visionとチャンピオンズ実装ポケモン候補の照合を検証した。

### 実装

- 場所: `poc/capture/RecognitionSources/`
- テスト: `poc/capture/Tests/CaptureRecognitionTests/`
- 入力: `CGImage`またはキャプチャ直後の`CVPixelBuffer`
- OCR: `VNRecognizeTextRequest`、`.accurate`、`ja-JP`、言語補正あり
- 照合: 日本語名を正規化後、Levenshtein距離1以内の一意な候補のみ採用
- 結果: `detected` / `noText` / `noMatch` / `ambiguous`を明示的に区別

ROIはReactの表示座標ではなく、映像ソース内の左上原点・正規化座標で管理する。詳細な決定理由は `docs/decisions/0001-normalized-source-frame-ocr-regions.md` を参照。

| --- | --- |
| 自分・左下 | `(0.06452, 0.86964, 0.14144, 0.06429)` |
| 相手・右上 | `(0.81141, 0.02500, 0.13896, 0.06429)` |

### ライブ交代検知（2026-07-18）

- 左右独立の状態機械で、8Hzの名前領域差分を監視。
- HUD非表示フレームは交代の証拠に数えない。
- 直近5サンプル中3回の変化に加え、表示中かつ確定時HUDとの差があり、直前フレームから安定した状態が3サンプル連続した場合に、公開状態を維持したまま確認用OCRプローブを開始する。
- プローブが現在と異なるポケモンを完全一致で返した場合だけ交代疑いへ遷移する。現在と同じならイベントを出さず比較基準を更新し、不成立なら変化履歴を破棄して次の視覚プローブを3秒間抑制する。
- 1バーストは異なる5フレーム。完全一致は3票、1文字補正は4票かつ信頼度中央値の条件を満たした場合だけ確定。
- 不成立時は最大3バーストまで再試行し、それでも確定できなければ`pokemon_detection_failed`を明示出力。
- 3秒ごとの低頻度`.accurate`プローブは交代候補の発見にだけ使い、単発結果ではBattleState更新イベントを出さない。対象Visionランタイムの`.fast`は日本語非対応のため使用しない。
- Visionは専用直列キューで実行し、キャプチャ・MJPEG配信キューをブロックしない。
- OCRリクエストに世代IDを付け、演出再開などで無効になった遅延結果は`stale_recognition_rejected`として明示的に拒否。
- `ipad-battle-hud-v1`と異なるアスペクト比・向きはエラーにし、iPhone / SwitchへROIを暗黙流用しない。
- iPad実機対戦では、初回のマスカーニャ対ガブリアスと、ガブリアスからムクホーク、マスカーニャからギャラドス、ムクホークからラウドボーンへの交代を正しく検出し、誤った種への確定は0件だった。
- 実機テストで通常の技演出による状態遷移の頻発を確認したため、安定した表示HUDを必要とする条件へ修正した。
- 2回目のiPad実機対戦では、マスカーニャ対カイリューと、カイリューからガブリアスへの交代を正しく検出し、誤った種への確定は0件だった。一方、安定して見える通常演出でも不要な状態遷移が残ることを確認した。
- この結果から、視覚差分だけでは公開状態を変更せず、異なる名前のOCR証拠を得てから交代疑いへ進む方式に修正した。
- 3回目のiPad実機対戦では、マスカーニャ対エルフーンと、エルフーンからラウドボーン、マスカーニャからギャラドスへの交代を正しく検出し、誤った種への確定は0件だった。通常演出と交代後約40秒の進行では不要な`transitioning`が発生せず、OCRゲートによる改善を確認した。
- エルフーンからラウドボーンは`transitioning`から約1秒で確定した。マスカーニャからギャラドスはHUD安定判定とOCR不成立が続き、確定まで約28秒を要したため、交代後の確定時間には改善余地が残る。
- 異なる名前を完全一致で確認済みの交代では、画面全体の静止を重ねて要求せず、即座に5フレーム合議へ進むよう修正した。交代確認中はHUD表示だけを要求し、HUDが一度消えた場合も3フレーム連続で再表示された時点から背景の動きに関係なく再開する。初回検出の画素安定条件は維持する。
